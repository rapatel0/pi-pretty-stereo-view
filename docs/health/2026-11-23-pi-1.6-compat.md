# Pi 1.6.0 compatibility audit — 2026-11-23

## Incident

Pi-Bolt 1.3.0 (Pi 1.6.0) crashed with an uncaught `TypeError` inside
`measureHeight` on any assistant message containing a thinking block:

```
TypeError: undefined is not an object (evaluating 'this.thinkingVisibilityOverrides.get')
  at renderPanelAssistant (extensions/pretty-tui/index.ts:1415)
```

Because the throw happened during the host's height-measure render pass, it
surfaced as an `uncaughtException` and killed the TUI. Reproduced 5x on
2026-11-23 with user config `pretty-tui.json`
`{ "enabled": true, "mode": "full", "sideBorders": false }`.

## Root cause

`extensions/pretty-tui/index.ts` vendors a copy of Pi's
`AssistantMessageComponent.render`/`updateContent` loop. Pi 1.6.0 changed the
host field the vendored copy dereferences:

| | Pi 1.5.x (pi-bolt 1.2.1 bundle) | Pi 1.6.0 (pi-bolt 1.3.0 bundle) |
| --- | --- | --- |
| declaration | `thinkingVisibilityOverrides = new Map;` | `thinkingVisibilityOverrides;` (undefined) |
| `setHideThinkingBlock` | `.clear()` | `= undefined` |
| host read | `.get(runIndex) ?? this.hideThinkingBlock` | `?.get(runIndex) ?? this.hideThinkingBlock` |
| per-run write | `.set(runIndex, !hidden)` | `??= new Map` then `.set(...)` |

In Pi 1.6.0 the map is legitimately `undefined` until the user clicks a
thought; the vendored copy assumed a `Map`.

## Fix

Single normalisation helper `thinkingOverrideFor(self, runIndex)` at module
scope in `extensions/pretty-tui/index.ts` — treats a missing map as an empty
override map — with provenance comments naming the vendored host method and
the Pi versions verified. All vendored reads go through it. Behaviour is
identical on Pi >= 1.4.0 (field is always a `Map`) and Pi 1.6.0 (undefined
until first per-run click). Backward-compatible; no user-visible change.

Regression probe: `test/thinking-visibility-probe.mjs` (in `npm test`). It
loads the real bundle through `test/harness.mjs`, patches the actual
`AssistantMessageComponent.prototype`, and renders (a) a Pi 1.6.0-shaped
instance (`thinkingVisibilityOverrides === undefined`), (b) a `Map` with
`true`/`false` per-run overrides (setting an override must be followed by
`updateContent`, mirroring the host click callback), (c) a message with no
thinking children, and (d) the item-3 sequence: per-run click shows the body,
global `setHideThinkingBlock(true)` (which resets the map to `undefined` on
1.6.0) hides it again, and a second click recreates the map through the
host's `??= new Map` path and shows it — all against the installed 1.6.0 host
module, so the reset/recreate behaviour is the real host's. Note the
compact-preview subtlety: a hidden thought's compact line is the thinking's
first line, so the probe asserts on a body marker placed on a later line.

## Drift audit (item 6) — triage of newly-optional host fields

Method (refined from the task prompt): extract candidate host fields from the
pi-bolt 1.2.1 and 1.3.0 bundles via `strings`, but **keyed by the enclosing
class**, then intersect with the `this.<name>` identifiers the extension
dereferences. The prompt's flat name-level `join` over-reports because the
bundles contain many unrelated classes with same-named fields.

- 67 names go `= INIT` (1.2.1) -> bare (1.3.0) at name level — matches "~67".
- Flat intersection with extension `this.X` reads: 22 names (not 1 as the
  prompt's prose implies — its conclusion was right, its method can't show it).
- Class-scoped intersection: genuine same-class drift in 2 names:
  - `thinkingVisibilityOverrides` @ `AssistantMessageComponent` — the crash
    above; the only one the extension dereferences. **Fixed.**
  - `options` @ `Resolver` — the Node DNS resolver bundled inside the binary;
    the extension's `this.options` reads are all on its own classes
    (`powerline/editor-performance.ts` constructor-assigns it). Not applicable.
- Spot-checked the prompt's counter-arguments, both hold in the 1.3.0 bundle:
  `AssistantMessageComponent`'s constructor assigns `this.hideThinkingBlock`
  and `this.outputPad` (lines 845422/845425 of the strings dump), so their
  bare declarations are always initialised; `cache`/`width`/`theme`/etc. are
  same-named fields on unrelated bundled classes (`Compiler`, `BlockRaster`,
  `MeasuredRows`, undici, AWS SDK exception classes, ...).

**Triage outcome: confirmed.** The only newly-optional field this extension
dereferences is `thinkingVisibilityOverrides`.

## Why `tsc` did not and will not catch this class of drift

The task prompt attributes the miss to devDependencies pinning 1.4.0. That is
only half right: even against 1.6.0 typings this stays invisible, because
(a) the patched host functions annotate `this: any`, and (b) the field is
`private` in the host `.d.ts`. The devDeps bump to 1.6.0 keeps the build
honest about what users run, but the runtime probe is the actual gate.

## Sibling state paths (item 3)

Pi 1.6.0's `setHideThinkingBlock` resetting `thinkingVisibilityOverrides` to
`undefined` is semantically identical to 1.5's `.clear()` — both wipe per-run
overrides on a global toggle. The extension's own state round-trips
independently of the host map:

- `patchedSetHideThinkingBlock` records into `explicitThinkingVisibility` /
  `fullThinkingVisibility` (WeakMaps) **before** delegating to the original,
  so the host's reset cannot erase extension state.
- `patchedUpdateContent` re-derives `this.hideThinkingBlock` from those
  WeakMaps plus the module defaults `fullThinkingHidden` /
  `compactThinkingHidden` on every content update.
- The stereo activity-pane reveal (`extensions/stereo-view/content.ts:266`,
  `source.setHideThinkingBlock(false)`) takes the same patched path; like the
  host's own global toggle it also clears per-run overrides — unchanged
  behaviour across Pi versions.
- Clean mode still never calls through in a way that mutates Pi's persisted
  `hideThinkingBlock` setting (invariant comment at the toggle handler,
  "Do not change Pi's persisted hideThinkingBlock setting in clean mode").

The click -> global toggle -> re-click sequence is additionally gated by
probe case (d) above.

## Optional hardening (item 7) — declined

Wrapping the vendored render so a `TypeError` silently falls back to the
native host render was considered and rejected: with
`thinking-visibility-probe.mjs` gating `npm test`, a loud crash at the next
host-shape drift is more actionable than degraded-but-quiet rendering (wrong
panels, lost source-row mapping for mouse hit tests) that could mask the real
defect in development and in the field.
